1. 一页看懂工程

本节回答：这是什么工程？技术栈分几层？目录大致怎么放？

1.1 工程定位

OpenReel Video 是一个浏览器端本地优先的专业视频编辑器。核心理念是：媒体尽量留在用户设备本地处理，服务端只做协作、市场 API 和代理转发等少量工作。

本地浏览器 / Electron │ ├── React UI：欢迎页、编辑器、面板、AI 对话 ├── Zustand Store：工程状态、时间线状态、UI 偏好 ├── @openreel/core：时间线、动作、渲染、字幕、导出领域规则 ├── @openreel/agent：把编辑能力注册成工具供 LLM 调用 ├── @openreel/collab：操作排序、冲突检测、多人协作 ├── @openreel/ui：基础组件库 └── Cloudflare：API 代理、协作房间、市场与 crash API

2. 浏览器在工程中的角色（Web 新手指南）

本节回答：如果你熟悉服务端或原生程序，Chrome 在这里到底是运行容器、UI 框架、媒体引擎，还是安全沙箱？答案是：它同时承担这些角色，但各管一段。

2.1 一句话理解

在这个工程里，浏览器相当于应用的“操作系统 + 显示屏 + 工具箱 + 保安”：

  • 工程代码负责“想做什么”：时间线怎么剪、撤销怎么记、AI 工具怎么调用、导出什么格式。
  • 浏览器负责“在哪里做、用什么能力做、受什么限制做”：把 React 组件画成画面、接收鼠标键盘事件、提供编解码/GPU/音频/存储 API，同时限制代码不能乱读磁盘。

可以把 Chrome 理解成“带安全边界的应用运行时”。我们的 Web 应用不是直接跑在操作系统上，而是跑在浏览器提供的沙箱里。

2.2 浏览器提供了什么，工程代码怎么用

浏览器提供的能力工程里的用途对应代码
HTML / CSS / JavaScript 引擎（V8、Blink）、DOM把 React 组件渲染成用户看到的界面；执行业务 JS。index.html、main.tsx、App.tsx、components/*
事件系统：click、drag、keyboard、pointer用户点击按钮、拖动片段、按快捷键，最终变成 store action。EditorInterface.tsx、services/keyboard-shortcuts.ts
File / Blob、MediaBunny、WebCodecs导入本地视频/图片；解封装、解码、编码；导出视频文件。packages/core/src/media/mediabunny-engine.ts、packages/core/src/export/webcodecs-backend.ts
WebGPU / Canvas2D、Web Audio API实时合成预览画面、执行特效着色器、播放和混音。apps/web/src/bridges/render-bridge.ts、packages/core/src/video、packages/core/src/audio
IndexedDB、localStorage、Service Worker自动保存项目、存媒体 Blob、保存偏好、离线缓存。auto-save.ts、project-manager.ts、service-worker.ts
fetch、CORS、COOP / COEP、权限系统调用 API、代理第三方服务、允许 SharedArrayBuffer、限制越权访问。apps/web/src/services/api-proxy.ts、apps/web/vite.config.ts、apps/web/public/_headers

2.3 一次“导入并导出”的协作过程

  1. 启动：Vite dev server 把 index.html 和 JS 模块送给浏览器；浏览器执行 main.tsx。
  2. 渲染 UI：React 创建 DOM，浏览器把它画成欢迎页或编辑器；这一步相当于原生应用的“窗口绘制”。
  3. 选择文件：用户选中 MP4。浏览器通过 File API 把文件包装成 File/Blob 交给 JS；代码拿不到任意磁盘路径。
  4. 解封装与解码：工程把 Blob 交给 MediaBunny；解码结果变成 OffscreenCanvas，由 WebGPU/Canvas2D 显示。
  5. 编辑：用户拖动片段，工程生成一个 Action；Zustand store 更新，bridge 通知渲染引擎重画预览。
  6. 导出：WebCodecsBackend 调浏览器的 VideoEncoder/AudioEncoder 编码，MediaBunny 负责封装，最后浏览器把文件下载到本机。
  7. 落盘：工程状态写入 IndexedDB；Service Worker 缓存静态资源，支持刷新恢复与离线打开。

2.4 浏览器不做什么

  • 不是服务端：默认不会把工程上传到云；云只用于协作/API/市场。
  • 不给任意文件系统访问：只能使用用户显式选择的文件或授权后的 handle。
  • 不懂剪辑语义：时间线、撤销、转场、字幕规则都在 @openreel/core。
  • 不保证所有编码格式：浏览器支持什么 codec 就能用什么；ProRes/MXF 等需要桌面原生 ffmpeg。
  • 不保证内存常驻：刷新页面内存清空，必须靠 IndexedDB/localStorage 恢复状态。

2.5 为什么推荐 Chrome / Edge

  • WebCodecs、WebGPU、SharedArrayBuffer 支持更完整。
  • 硬件编解码器与 GPU 加速更容易启用。
  • DevTools 可直接看 DOM、Console、Network、Application(IndexedDB)、Performance。
  • 其他浏览器也能用，但可能走 Canvas2D 回退或缺少某些编码能力。

2.6 浏览器版与桌面版的能力边界

能力浏览器版桌面版
文件访问用户选择的 File/Blob，受沙箱限制。可结合 Electron 访问更多本地路径与 sidecar。
编解码WebCodecs + MediaBunny，受浏览器 codec 支持限制。原生 ffmpeg 覆盖 ProRes、DNxHR、MXF 等专业格式。
渲染WebGPU 优先，Canvas2D 回退。还可使用原生 Aurora 渲染核心。
后台计算Web Worker + WASM。可调用原生进程与更多 CPU/GPU 能力。
持久化IndexedDB/localStorage，受浏览器配额限制。可配合本地文件系统与备份流程。

2.7 Web 新手排错速查

现象先怀疑什么怎么查
页面空白JS 报错或缺 WASM 产物。Console；确认执行过 pnpm build:wasm。
SharedArrayBuffer 报错缺少 COOP/COEP 头。Network 看响应头；自建代理要补 _headers。
导入素材失败浏览器不支持该 codec。看 MediaBunny Input 的轨道与 canDecode()。
预览卡顿WebGPU 不可用，回退 Canvas2D。DevTools Performance、chrome://gpu。
导出格式不可用浏览器编码器不支持。换 H.264/VP9 或使用桌面版。
刷新后状态丢失只改了内存，没写 IndexedDB。DevTools Application 看 IndexedDB/localStorage。
界面没有中文当前版本没有 UI i18n。见 英文菜单对照 与 第 12 章。

给非 Web 程序员的最后提示：不要把浏览器只看成“显示网页的壳”。在这个工程里，它同时是运行时、UI 渲染器、媒体能力提供者、存储容器和安全边界。工程代码负责业务规则，浏览器负责把这些规则落成用户能看到、能操作、能保存的结果。

4.3 三条分流

分流路径与主干的关系
AI 编辑流自然语言 → LLM tool call → live-host → ActionExecutorAI 不直接改 store，而是生成 action，因此可像手动编辑一样撤销。
协作流本地 action → op → RoomCore 排序 → 远端重放 → ActionExecutor同步单位是 action 而非整份工程，带宽小且冲突可控。
导出流ExportDialog → ExportRunner → 编码 → 下载/队列只读工程快照，属于数据流的“消费者”。

4.4 容错与回退

  • 无 WebGPU：回退 Canvas2D；CI 无 GPU 环境也依赖此路径。
  • WASM 加载失败：FFT/节拍检测等模块回退 JS 实现。
  • 桌面原生后端缺失：creation 引擎回退 CPU 参考实现。
  • 面板崩溃：PanelErrorBoundary 隔离；工程崩溃：自动保存槽位 + RecoveryDialog 恢复。

7. 状态管理与持久化

本节回答：工程状态放在哪？为什么刷新后还能恢复？

7.1 Zustand 状态中心

10. 音视频编辑操作的技术原理

本节回答：拖动片段、裁剪、分割、贴图、加字幕、转场、变速、调色、混音，这些操作在程序里到底发生了什么？转场时声音又会不会自动跟着渐变？

10.1 核心原则：编辑不修改原始媒体

本工程采用非破坏性编辑。原始视频/音频文件始终只读，时间线上的“片段”只是对它的引用加一组参数：从哪里进、从哪里出、放在什么时间、用什么效果、速度多少、音量多少。

原始媒体文件（只读） │ 解码 ▼ 帧 / 音频采样（临时） │ 按时间线参数重新组合 ▼ 预览画面 / 导出文件

可以把 Project/Timeline 理解成一张“菜谱”，把媒体文件理解成“食材”。编辑操作改的是菜谱；预览和导出才按菜谱重新做菜。

10.2 三层数据模型

层数据作用
媒体层Blob、解码后的帧、音频采样提供真实素材内容，通常由 MediaBunny / WebCodecs / 原生解码器产生。
编辑层Timeline、Track、Clip、Action描述“在什么时间、用哪段素材、施加什么参数”。
渲染层WebGPU 纹理 / Canvas 画面、Web Audio 节点图把编辑层描述实时变成用户看到的画面与听到的声音。

Clip 上常见字段包括 inPoint、outPoint、effects、transform、volume、keyframes、speed、colorGrading 等，见 packages/core/src/types/timeline.ts。

10.3 所有编辑操作的通用链路

  1. 用户在界面上点击、拖拽或输入；组件把事件翻译成一个语义动作。
  2. 动作进入 ActionExecutor：校验 → 调用 handler 修改工程 → 记录逆动作。
  3. Zustand store 更新内存状态，界面重新渲染。
  4. Bridge 把变化同步给渲染/播放/音频引擎，预览刷新。
  5. 需要落盘时写 IndexedDB；需要成片时进入导出引擎。

因此，AI 编辑、多人协作与手动编辑走的是同一条路：最终都变成 Action。

10.4 常见操作背后的技术原理

操作程序里发生了什么关键点
选择 / 移动片段改变片段在轨道上的起始时间。不复制媒体；只改时间坐标。
分割 Split把一个 Clip 拆成两个，分别设置新的 inPoint/outPoint。源文件没有被切开；只是边界变了。
修剪 Trim调整 inPoint 或 outPoint，改变使用源的哪一段。对应 action 如 clip/trim、clip/trimToPlayhead。
删除 / 波纹删除从轨道列表移除片段；波纹删除还会把后续片段整体前移。普通删除留空，波纹删除闭合空隙。
复制 / 粘贴把片段描述（含效果和参数）序列化到剪贴板，再写入目标时间。复制的是“引用 + 参数”，不是媒体二进制。
转场在两个片段接缝处放置 Transition，渲染时按进度混合前后帧。转场是渲染规则，不是写回文件。
变速把时间线时间映射到不同的源时间，必要时做帧采样/插值。音频还要做时间拉伸与音高修正，见 speed、speedKeyframes。
关键帧 / 动画在不同时间点保存属性值，渲染时对中间帧做插值。位置、缩放、透明度、音量、效果参数都可以动画化。
文字 / 字幕把文字与样式作为图层叠加到画面；字幕可从 SRT/VTT 或转录生成。导出时还可选把 CEA-608 字幕写进 H.264 SEI。
特效 / 调色给片段挂上 Effect 或 colorGrading 参数；渲染器逐帧应用。视频走 WGSL 着色器或 Canvas 滤镜，音频走 Web Audio 节点。
音频混音每个轨道/片段形成 Web Audio 节点：增益、声像、EQ、压缩、自动化。播放实时计算；导出前用 OfflineAudioContext 离线混成一条或多条音轨。
多机位多个轨道共享同一时间轴；每个时刻选择哪个轨道作为活动画面。切换的是“视角源”，片段本身仍未改动。

10.5 贴图、字幕与视频转场的专门机制

前面把编辑操作看成“改参数”，这三类功能最容易让人误以为是直接改画面文件。实际上它们仍然是独立数据 + 渲染时叠加/合成：贴图是 overlay 图层，字幕是按时间显示或导出的文本轨，转场是两个相邻片段在接缝处的合成规则。

视频转场：同一时刻取两路帧，再按进度合成

转场保存在 Track.transitions 中，引用两个相邻片段 clipAId/clipBId，或某一片段的边缘 edge: "in" | "out"。引擎要求两片段在同一轨道且相邻，容差约 1 毫秒。在时间 T 落入转场窗口时，程序同时解码 A 与 B 在 T 这一时刻的画面，计算进度 progress，再用 TransitionEngine 合成一帧输出。

时间 T 落入转场窗口 │ ├── 解码 A 在 T 时刻的帧 └── 解码 B 在 T 时刻的帧 │ ▼ 计算 progress（0 → 1）+ 缓动曲线 │ ▼ TransitionEngine：crossfade / wipe / slide / push / zoom / ... │ ▼ 输出这一帧的转场画面

常见类型包括 crossfade、dipToBlack、dipToWhite、wipe、slide、push、zoom、glitch、flash 等 24 种。默认两片段转场以切点为中心，窗口为 [切点 - duration/2, 切点 + duration/2]；也可由 params.alignment 改成完全在切点前或切点后。预览和导出最终都复用 VideoEngine.renderFrame() 里的活跃转场查找与渲染，所以不是两套完全不同的算法。

转场如何确保音画同步

这里要区分两个概念：时间对齐是默认存在的，音频交叉淡化不是默认存在的。转场使用的是同一条时间线秒轴：画面从 A/B 两路按 T 取帧，音频 clip 也按 T 映射到各自的源时间。因此播放头、画面转场进度、音频调度和导出帧都锚定在同一个 timeline 时间上，不会各走各的时钟。

但是，视频做了 crossfade 并不代表声音自动 crossfade。源码中音频淡变只有在 transition.params.audioFade === true 时才会启用；默认 false，且默认转场参数不会自动写入该开关。启用后，对 clip-to-clip 转场，A 的尾部做 duration / 2 的 fade out，B 的头部做 duration / 2 的 fade in；对单 clip edge 转场使用完整 duration。音频淡变按 clip edge 锚定，并不复用视频转场的 alignment 窗口。

场景画面声音
只加视频转场按转场窗口混合两路画面。没有自动 crossfade，声音按各自 clip 的时间、音量与自动化继续播放。
开启 audioFade仍按视频转场规则。A 尾部淡出、B 头部淡入；时长与视频转场对齐到同一 clip edge，但 alignment 规则不同。
实时预览requestAnimationFrame 驱动画面。AudioContext.currentTime 作为时钟参考；音频节点提前调度并补偿路由/效果延迟。
导出按 time = frame / frameRate 固定步长逐帧求值。音频在同一 exportStart/exportDuration 范围内离线混音，再编码封装。

10.7 音画同步是怎么做到的

工程内部时间统一用秒（浮点数）表示。视频按帧率换算成帧号，音频按采样率换算成采样点索引。播放时浏览器用 requestAnimationFrame 驱动画面，用 AudioContext.currentTime 作为音频时钟参考；导出时不再依赖实时时钟，而是按固定时间步长逐帧计算。转场本身也遵守这套统一时间轴；转场期间是否让声音一起淡入淡出，则取决于 audioFade 开关，见 10.5。

10.8 为什么采用这种设计

  • 可撤销：每步操作都有逆动作，数据没有被真正破坏。
  • 可协作：同步的是小体积的 action，而不是整段视频。
  • 可被 AI 调用：工具调用最终也生成 action。
  • 预览快：只重新计算受影响的部分，媒体仍从缓存读取。
  • 导出可控：同一份编辑描述可以导出不同分辨率、码率和格式。

17.4 先记住的 8 个结论

  • MediaBunny 做 demux/mux，WebCodecs 主要做 encode；不要把浏览器的解码角色想当然套过来。
  • 预览层看到的是 ImageBitmap/canvas，不是裸 VideoFrame。
  • 时间统一用秒（浮点数）；导出帧解码用前向游标而非随机帧号。
  • 浏览器导出主链是 WebCodecsBackend + MediaBunny，ffmpeg 不是浏览器端必经环节。
  • 默认关键帧间隔 60 帧（30fps 下 2 秒）；rateControl: "quality" 是桌面 CRF 语义并忽略 bitrate。
  • HDR 导出依赖 hvc1 Main10、BT.2020 PQ/HLG；预览是 SDR tone mapping 后的结果。
  • 音频编码可为 AAC/Opus/MP3 等，取决于容器与浏览器；桌面端还有 WAV 与多声道策略。
  • ProRes、DNxHR、XDCAM、AVC-Intra、MXF、透明通道、高位深必须走桌面原生 ffmpeg。

17.5 最容易误判的限制

限制表现原因 / 处理方式
浏览器无 WebGPU预览回退 Canvas2D，4K/复杂特效性能下降。功能仍可用；CI 无 GPU 环境依赖此路径。
CBR 尽力而为浏览器端恒定码率受编码器实现影响。bitrateMode: "cbr" 会映射到 WebCodecs 的 constant 模式，但不保证所有平台精确恒定。
采集卡输入桌面端帧率偏低。逐帧 RGBA 经 IPC 传输，开销大。
HDR 无法 smart render即使源/预设一致也重编码。高色深与 HDR 会触发模拟器检查并禁用流复用。
离线渲染不是逐帧输出没有标准 PNG/JPEG 序列导出。底层渲染器支持磁盘帧，但产品层未暴露。
AV1 导出编码工作但封装失败。MediaBunny 当前不支持 AV1 MP4 封装；优先用 VP9/WebM。

一句话上手策略：先沿着“编码器参数 → 编码与封装 → 解封装与取帧 → 预览渲染”倒着读。你已经懂 codec 原理，真正需要掌握的是这个工程如何把 ExportSettings 翻译成 WebCodecs/ffmpeg 调用，以及如何把时间线变成帧。
